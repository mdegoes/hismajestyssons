# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

There is no build step, package manager, or test suite for the site itself — this is a static site. (The one exception is `stripe-setup/`, a standalone Node tooling directory with its own `package.json` used only to provision Stripe objects — see Art print shop below. It isn't loaded by any page and isn't a build step for the site.)

```bash
# Serve locally (either works)
python3 -m http.server 8000
npx serve .
```

Open `http://localhost:8000`. An internet connection is required for full fidelity: Google Fonts (Libre Baskerville) and the React/Babel CDN scripts used by `index.html` both load remotely.

## Architecture

### Two rendering strategies, split by page

- **`index.html` (home) is a React app.** It loads React 18 + ReactDOM + `@babel/standalone` from unpkg, then `app.jsx` as an in-browser-compiled `text/babel` script (no bundler — Babel transforms JSX at page load). `app.jsx` defines and `App()` mounts Nav/Hero/Explore/Manifesto/Foot, in that order — that's the whole homepage. See Homepage layout below for why Explore sits between Hero and Manifesto rather than the other way around.
- **Every other page** (`art.html`, `music.html`, `family-prayer.html`, `worthy-books.html`, `worthy-men.html`, `armory.html`, `theme-preview.html`) **is plain static HTML** with a small vanilla `<script>` at the bottom that toggles the `.nav`'s `data-scrolled` attribute on scroll and wires up the mobile hamburger menu (see Mobile nav below). No React on these pages.

Don't assume a change to `app.jsx` affects any page besides `index.html`.

### Homepage layout (Hero → Explore → Mission)

- `index.html`'s section order is **Hero, then Explore (Lead/Learn/Make War/Build), then Mission, then Footer** — deliberately in that order so a first-time visitor sees the four category bands right after the hero, not after a full mission statement. Mission used to render directly under Hero; it was moved down to sit just above the footer so Explore isn't pushed below the fold.
- `Hero()` is intentionally minimal now: an eyebrow, a one-line title, and a short strap — no photo, no CTA. It used to include a `hero-photo` (`assets/images/home_page.png`, now unused by any page) and a "Read the Mission ↓" button; both were removed so the hero takes as little vertical space as possible and the first Explore band is visible with little to no scrolling, especially on mobile. `home.css`'s matching `.hero-right`/`.hero-photo`/`.photo-caption`/`.hero-meta`/`.hero-actions` rules were deleted along with the markup — don't resurrect either without a real reason to bring the photo back.
- `Explore()` (in `app.jsx`) renders four `ExploreBand` full-bleed photo sections, one per nav category, in the same Lead/Learn/Make War/Build order as the nav dropdowns:
  - Lead → `assets/images/7_days_of_prayer.png` → CTAs "Worship" (`music.html`), "Pray" (`family-prayer.html`)
  - Learn → `assets/images/worth_a_read.png` → CTAs "Books" (`worthy-books.html`), "Men" (`worthy-men.html`)
  - Make War → `assets/images/worth_a_follow.png` → CTA "Take Up Arms" (`armory.html`)
  - Build → `hms-art/01-the-church-sm.jpg` → CTA "Browse the Prints" (`art.html`)
  - CTA copy is deliberately short and action-oriented (verb-first or a plain plural noun), not the sub-page's own nav-dropdown label — don't reuse `NAV_DROPS`' link text here (e.g. Learn's dropdown says "Worthy Books"/"Worthy Men", Explore says "Books"/"Men").
  - Each `ExploreBand` is a fixed-contrast, not theme-driven, dark-scrim-over-photo band: the paper-white text and the warm gold (`#C9A75D`) `em` accent are hardcoded in `home.css` rather than pulling `--ink`/`--paper`/`--accent`, since legibility here depends on the photo underneath, not the light/dark scheme. CSS lives in `home.css`'s `.explore*` rules, same "homepage-only, not promoted to `site.css`" convention as `.hero*`/`.manifesto-v2`.
  - The Build band's image (`hms-art/01-the-church-sm.jpg`) is a real print asset with a baked-in white matte border (~2.7% of width / 3.5% of height) plus corner branding (title card, QR code) — shown at plain `object-fit: cover` it leaves a visible white sliver at the section's true edges. `ExploreBand`'s `image` prop takes an optional `zoom` factor (`1.15` here) applied as an inline `transform: scale()` on the `<img>`, which crops the border out regardless of viewport aspect ratio; `.explore-band`'s existing `overflow: hidden` clips the overage. Only this band needs `zoom` — the other three are plain photos with no border baked in.

### Styling: shared tokens, single source of truth

- `site.css` defines the shared design tokens (`:root` custom properties for `--paper`, `--ink`, `--accent`, fonts, spacing, plus `--radius-pill`/`--radius-soft`/`--shadow-soft`) along with `[data-scheme="ink"]` dark-mode overrides, nav, buttons, footer, and a handful of cross-page components (`.num-badge`, `.arrow`, `.idx`/`.roman` core recipes, `.roster-list`/`.roster-row`/`.roster-photo`). **Every page links it**, including `index.html` — there is no more forked copy of the tokens anywhere.
- `index.html` additionally links `home.css` for hero/explore/manifesto markup that's genuinely unique to the homepage (`.hero*`, `.explore*`, `.manifesto-v2`/`.m-*`, `.reveal`). Every other page keeps its own page-specific layout in its own inline `<style>` block (e.g. `art.html`'s `.collection-plate`) on top of the two shared stylesheets.
- Only promote a page-specific class into `site.css` when it's genuinely duplicated across ≥2 real pages (not counting `design-system.css`'s aspirational "canonical" section as a second usage) or fills a gap the design-system page already documents. Don't add tokens/classes speculatively for a single current usage.

### Theming (light/dark)

Theme is a first-class, user-facing feature (not a dev tool) — there is no accent-color or density picker anywhere on the site anymore; the only user control is the light/dark toggle.

- `theme.js` runs synchronously in `<head>` (before first paint, to avoid FOUC) and sets `data-scheme` (`"ink"` or `"paper"`) on `<html>`. On first visit (no `localStorage['cc-scheme']` yet) it follows the OS `prefers-color-scheme` media query, falling back to `"ink"` if that's unsupported/unset; once a visitor manually toggles, that choice is saved to `localStorage['cc-scheme']` and wins from then on.
- If no manual preference is saved, `theme.js` also listens for OS `prefers-color-scheme` **changes** and live-updates `data-scheme` accordingly.
- `window.CC.toggleScheme()` flips the scheme, persists it, updates the toggle button's tooltip/`aria-label` (via `_ccUpdateTooltips`), and fires a `cc-schemechange` event.
- `theme.js` adds `html.theme-ready` one frame after load (via `requestAnimationFrame`), which is what enables the `0.25s` background/color/border-color transitions in `site.css` (linked by every page, including `index.html`) — this ordering matters: transitions must stay off until after first paint or you get a FOUC-adjacent flash.
- On `index.html`, `app.jsx`'s `ThemeToggle` no longer holds its own state — it just reads `window.CC.getScheme()` and re-renders on `cc-schemechange`, calling `window.CC.toggleScheme()` directly on click. There is no more `useTweaks`/`TweaksPanel` wiring on the home page.
- `tweaks-panel.jsx` (the old accent/density/scheme dev-tool control kit) has been deleted along with its design-system Dev Tool section — it was fully orphaned (no page loaded it) and kept no reference value once theme became a first-class OS-aware feature.

### Mobile nav (hamburger menu)

- Below 720px, `.nav-links` hides itself and a `.nav-toggle` hamburger button (in `.nav-end`, next to the theme toggle) becomes the only way to reach nav links. Clicking it sets `data-menu-open="true"` on `.nav`, which drops `.nav-links` into an absolutely-positioned panel below the bar; the CSS lives in `site.css`, shared by every page including `index.html`.
- On static pages, each trailing `<script>` queries `.nav-toggle`, toggles `data-menu-open` on click, and closes the menu when a `.nav-links a` is clicked. It also flips the button's `aria-expanded` **and** `aria-label` (`"Open menu"` / `"Close menu"`) — don't drop the `aria-label` update when touching this script, it's easy to regress into a static label that never reflects state.
- On `index.html`, `app.jsx`'s `Nav` component holds `menuOpen` in React state instead and does the equivalent (`data-menu-open`, `aria-expanded`, `aria-label` all derived from state); it also closes the menu on nav-link click via a wrapped `jump()` handler.
- There's no click-outside-to-close or Escape-to-close handling anywhere (static pages or React) — closing only happens via the toggle button itself or clicking a link. That's consistent site-wide, not an oversight to "fix" on just one page.

### Nav dropdowns (Lead / Learn / Make War / Build)

- The top nav is **Mission** (a single plain link/scroll-jump to `index.html#manifesto`, not a dropdown) followed by four sibling `.nav-drop` wrappers: **Lead** (Music → `music.html`, Seven Days of Prayer → `family-prayer.html`), **Learn** (Worthy Books → `worthy-books.html`, Worthy Men → `worthy-men.html`), **Make War** (a single "The Armory" link → `armory.html`, see "The Armory" below), and **Build** (a single "Art" link → `art.html`). Each `.nav-drop` is a toggle-only `.nav-drop-trigger` `<button>` (not a link — clicking it only opens/closes the panel) plus a `.nav-drop-panel` listing that category's links. Make War and Build render the same dropdown chrome as Lead/Learn even though each currently reveals only one link — kept uniform deliberately, for when either grows more sub-items.
- There is no more "all resources" hub page (`resources.html` was retired) — each dropdown panel links straight to its member pages, no intermediate index.
- Opens on **click or hover** (desktop): each `.nav-drop` gets `mouseenter`/`mouseleave` listeners (React: `onMouseEnter`/`onMouseLeave` on the same div) that call the same `setDropOpen` state as the click handler — no separate hover-specific mechanism. The listeners are on the whole `.nav-drop` wrapper (trigger + panel together), not just the trigger, so moving the mouse from the trigger down into the panel doesn't prematurely close it. Harmless on mobile — touch devices don't fire `mouseenter`/`mouseleave` in a way that matters, so the accordion's click-only behavior there is unaffected.
- **Only one dropdown may be open at a time.** With four siblings instead of one, opening or hovering any `.nav-drop` closes every other one that's currently open (accordion behavior, both desktop hover/click and the mobile hamburger's nested accordion). Static pages implement this with a `closeOtherDrops(except)` helper called before every open; `app.jsx`'s `Nav` gets it for free from a single `openDrop` state variable (`null | 'lead' | 'learn' | 'makeWar' | 'build'`) instead of one boolean per dropdown — setting it to a new key naturally closes whichever one was open.
- The desktop panel's visual card (background/border/radius/shadow/vertical padding) lives on `.nav-drop-inner`, **not** `.nav-drop-panel` — `.nav-drop-panel` itself is only the positioned hit-box, with `padding-top: 14px` standing in for what used to be a `top: calc(100% + 14px)` gap. That's deliberate: a `top` offset leaves genuinely empty space between the trigger and the panel that belongs to neither element's hit-box, so the cursor briefly exits `.nav-drop` while crossing it, firing `mouseleave` and closing the dropdown before the user can reach an item — the classic "dropdown gap" bug. Padding is part of the box's hit-test area, so the same 14px visual gap no longer breaks hover. If this ever needs adjusting, resize the gap via `.nav-drop-panel`'s `padding-top`, not by reintroducing a `top` offset.
- A single `data-open` attribute on each `.nav-drop` drives both presentations via CSS alone, mirroring the `data-menu-open` pattern above — no separate open/close mechanism per breakpoint. Desktop: `.nav-drop-panel` is an absolutely-positioned floating panel (`opacity`/`visibility`/`transform`, same timing as the mobile menu panel). Mobile (≤720px, nested inside the already-open hamburger menu): the panel switches to `display: grid; grid-template-rows: 0fr → 1fr` for the accordion expand/collapse — deliberately **not** `max-height`, which would need a fragile hand-picked max value and eases unevenly once real content is shorter than that value. The `grid-template-rows` technique auto-sizes to real content height with no JS measurement; it needs the `.nav-drop-inner` wrapper div (with `overflow: hidden`) already present in the markup.
- Static pages wire a `setDropOpen(drop, open)` helper (same shape as `setMenuOpen`) plus `closeOtherDrops` in the trailing `<script>`, applied to every `.nav-drop` found via `querySelectorAll`; `app.jsx`'s `Nav` uses the single `openDrop` state var instead. In both, closing the outer mobile menu (via the hamburger toggle) also resets every dropdown's open state (`closeOtherDrops(null)` / `setOpenDrop(null)`) — don't let a re-opened mobile menu show an accordion section still expanded from last time.
- Current-page indication splits in two: `data-active="true"` on the trigger (styled identically to `.nav-links a[aria-current="page"]`, via a combined selector since the trigger is a `<button>` not an `<a>`) when the visitor is anywhere in that category's family of pages (e.g. Lead is active on both `music.html` and `family-prayer.html`), plus real `aria-current="page"` on whichever specific panel link matches the current page.
- CSS lives in `site.css`, shared by every page including `index.html` — unchanged by the move from 1 dropdown to 4; the same `.nav-drop`/`.nav-drop-trigger`/`.nav-drop-panel`/`.nav-drop-inner` rules apply to every instance, since `.nav-links` already supports an arbitrary number of sibling `.nav-drop`s.
- `.nav-drop-panel a` deliberately does **not** redeclare `font-family`/`font-size`/`letter-spacing`/`text-transform`/`font-weight` — it inherits all of that from `.nav-links` (which the panel is nested inside), guaranteeing it always matches the top-level Mission/Lead/Learn/Make War/Build styling exactly. It previously had its own copy of those properties with a typo'd `letter-spacing` that drifted from `.nav-links`; don't reintroduce an independent declaration here.
- The global `button { font: inherit; ... }` reset (top of `site.css`) also carries `text-transform: inherit; letter-spacing: inherit;` — browsers' default UA stylesheet resets `text-transform`/`letter-spacing` on form controls, and neither is part of the `font` shorthand, so without this the `.nav-drop-trigger` `<button>` would silently fall back to normal-case/default-spacing text instead of matching its `<a>` siblings in `.nav-links`. This is why `.nav-drop-trigger` needs no explicit uppercase/letter-spacing rule of its own — same "inherit, don't redeclare" principle as the panel links above.

### Footer site nav

- `.foot` is a 3-column grid (stacks to one column ≤720px): `.foot-brand` (logo mark + "Deus vult", side by side in a row — logo on the left, tagline immediately to its right), a real `<nav class="foot-links">` covering every page, and `.foot-social` (Instagram/YouTube, unchanged, sits at the right edge). Same markup shape across every static page's footer and `app.jsx`'s `Foot()`.
- `.foot-links` mirrors the top nav's Mission/Lead/Learn/Make War/Build grouping, but every item stays a real `<a>` — there's no separate hub page for a category name to link to, so Lead/Learn/Build's category name links straight to its first sub-item's page (e.g. "Lead" → `music.html`), with the actual sub-items listed right below it as `.foot-sub` (just a lighter `--ink-2` color, no indent — an indent was tried first but reads as a layout bug, not a hierarchy cue, so it was removed). Make War has no sub-items yet, so it's just its own single link, no `.foot-sub` row beneath it.
- `.foot-brand`'s logo is 72px and theme-aware (black in light mode, inverted white in dark mode, same as the nav logo) — this needs its own `.foot-brand .sigil img { width: 100%; height: auto; }` + `[data-scheme="ink"] .foot-brand .sigil img { filter: invert(1); }` rules in `site.css`, shared by every page. Don't assume `.sigil` sizes/inverts itself automatically: that only happens inside `.mark` (the nav's own wrapper class, per the `.mark .sigil img` rule and the existing gotcha noted below) — a plain `.sigil` outside `.mark` renders at its raw SVG intrinsic size (600×488px) with no dark-mode handling unless its own ancestor gets the equivalent rules, which is exactly what broke here the first time `.foot`'s wrapper was renamed from `.mark` to `.foot-brand` without carrying the sizing/invert rules along.

### Content structure

- `assets/` — brand assets (e.g. `logo-vertical.svg`, inverted via CSS filter in dark mode).
- `assets/images/` — real photography wired into placeholder slots on `index.html` (hero) and `music.html` (album cover). `assets/images/book-covers/` holds book cover thumbnails for `worthy-books.html`, sourced from Open Library's covers API and publisher (Canon Press) CDN URLs rather than supplied by the user — if more books get added later and a cover search comes up empty on Open Library, try the publisher's product page next.
- `assets/images/follow-photos/` holds `worthy-men.html`'s `.person-photo` images (circular, `aspect-ratio: 1/1`, `border-radius: 50%` — deliberately round, not the book shelf's rectangular `.book-cover`). 10 of the 12 roster entries have a real photo; **Stephen Wolfe and Josh Haymes are still an empty placeholder** (`<div class="person-photo"></div>`, no `<img>`) because no confidently-official photo source turned up for either — don't fill those in with a scraped social-media photo, wait for a real source or a supplied file. Pulling photos directly from people's X/Instagram accounts was explicitly ruled out: X's fetch returns 402 (paywalled API), Instagram serves a placeholder icon to non-authenticated requests, and even if either worked, rehosting a scraped social photo is a real copyright/ToS risk for real people. Instead, each photo was sourced from an official press/media/bio page and downloaded via direct URL, then normalized to JPEG: Wes Huff (wesleyhuff.com), John Lovell (Penguin Random House author page — his book publisher), Doug Wilson, Nick Freitas, and Michael Knowles (Wikimedia Commons, which carries an explicit reuse license per file — check the file's license terms before using elsewhere), Brian Sauvé (his own site, briansauve.com — Squarespace-hosted images need a `?format=` query param or they 1-byte-fail), Toby Sumpter (tobyjsumpter.com), Michael Foster (East River Church's staff page), Auron MacIntyre (his official Blaze Media profile page), and Wall Builders (David Barton's headshot from wallbuilders.com's own speaker page, standing in for the org). These are lower-risk than a scraped personal photo but still not unambiguously free-to-reuse in every case (aside from the Wikimedia Commons ones) — if this site's use ever gets questioned, revisit rather than assuming it's settled.
- Those same two image containers (`.hero-photo` in `index.html`, `.album-cover` in `music.html`) are deliberately sized at `width: 66.6667%` of their grid/flex cell rather than the full cell, aspect-ratio preserved so both dimensions shrink together — the images read as too large at full width. Each is pinned to the outer edge of the page (away from its adjacent text) via `align-self: flex-end` (hero, right-hand column) or `justify-self: start` (album cover, left-hand column), so the shrink reads as intentional margin rather than a layout gap. If more photo slots get added later, follow the same 66.6667%-plus-edge-alignment pattern rather than full-bleeding the container.
- `hms-art/` — the artwork collection shown on `art.html`; each piece ships a full-size and a `-sm` thumbnail JPG, numbered by display order (`01-...`, `02-...`, etc).
- `uploads/` — source images supplied by the user (raw material, not necessarily used directly on-site).
- `screenshots/` — design exploration captures, reference only, not loaded by any page.
- `CNAME` — GitHub Pages custom domain (`hismajestyssons.com`); this repo deploys via GitHub Pages directly from static files. Pages are normally plain files at the repo root; a page needs its own folder with an `index.html` only if it wants a clean, extension-less URL (see `design-system/` below).
- `assets/favicon.ico` (multi-size: 16/32/48/64px), `assets/favicon-16x16.png`, `assets/favicon-32x32.png`, `assets/apple-touch-icon.png` (180×180, for iOS) — the site favicon, generated from a single source crown-mark PNG. Linked via `<link rel="icon">`/`<link rel="apple-touch-icon">` in every page's `<head>` (root pages reference `assets/...`; `design-system/index.html` uses `../assets/...`). The source image has an opaque white background (not transparent), so the favicon renders as a white square with a black crown rather than blending into dark browser chrome — that's a known cosmetic tradeoff, not a bug, unless someone supplies a transparent-background version. There's no web manifest / Android/PWA icon sizes, just the standard favicon + apple-touch-icon set.

### Design system reference (`/design-system`)

- `design-system/index.html` + `design-system/design-system.css` — a live, un-indexed catalog (`<meta name="robots" content="noindex, nofollow">`, not linked from any nav) of every color, type style, spacing value, and component pattern in use across the site, organized as tokens → atoms → molecules → organisms. It's the canonical reference: **when adding or changing a component pattern, check here first, and update this page too so it doesn't drift from reality.**
- It reuses real classes from `site.css` directly (`.btn-primary`, `.eyebrow`, `.back-link`, etc.) so those specimens can't silently go stale. Page-specific patterns that don't have a shared class yet (`.photo-tag`, `.goto`, follow/piece cards) get their CSS copied into `design-system.css` as the documented spec.
- It also **introduces two proposed classes that remain doc-only, not shipped**: `.divider` (would consolidate `.collection-plate` in art.html and `.tracks-head` in music.html) and `.list-row` (would consolidate `.track`/`.book`/`.forthcoming-list li`'s row-heading typography). Both were deliberately left unmigrated: `.tracks-head` is flexbox while `.divider`'s draft is a grid (forcing them together needs a markup rewrite for a cosmetic-only payoff), and the `.list-row` row-heading recipe would touch 32 individual elements across 4 files for a pure-CSS-bytes win with no bug behind it. Don't adopt either without a fresh reason to revisit.
- Separately, `.roster-list` / `.roster-row` / `.roster-photo` (+ `--square`/`--circle` shape modifiers) **are shipped**, in `site.css` — the real shared skeleton behind `.shelf`/`.book`/`.book-cover` (worthy-books.html) and `.roster`/`.person`/`.person-photo` (worthy-men.html). They're applied *alongside* those original classes (additive markup, e.g. `class="book roster-row"`), never replacing them, because `.book`/`.person`/`.filter-select-wrap` are queried directly by each page's inline filter `<script>`.
- `worthy-books.html` no longer groups books into per-category sections (it used to be the 4th `.divider`-style pattern, via `.shelf-section` — now retired). It's a single flat `.shelf` list; each `.book` carries `data-category` and a `.book-tag` eyebrow naming its category, and a `.book-filters` row of `.chip` buttons (also copied into `design-system.css` as a documented atom) filters the list client-side by toggling the `hidden` attribute on non-matching `.book` elements. Categories are currently: History & The Faith, The Home & Marriage, Child Training & Sons, Work, Calling & The World.
- Every `.book` on `worthy-books.html` is a real, published title now (title, author, cover image under `assets/images/book-covers/`, and at least one buy link) — there are no more `/// title of the volume` / "Forthcoming" placeholder rows. The 4th grid cell is either a plain `<div class="meta">Forthcoming</div>` (unannounced book) or a `.book-links` wrapper holding one or more `<a class="btn-ghost buy-link">` retailer links (Amazon always; Canon Press too when the title is one of theirs — check `canonpress.com` before assuming a book isn't there, most of this shelf is Canon Press). The mobile `@media (max-width:720px)` rule repositions `.book .meta` and `.book .book-links` identically as a single grid item — don't reposition individual `.buy-link` anchors, they're nested inside `.book-links` now, not direct grid children.
- `worthy-men.html` was rewritten from a 3-column `.band`-grouped `.follow` card grid (all `/// name` placeholders) to the same flat-list-plus-filter-chips shape as `worthy-books.html`: a flat `.roster` list of `.person` rows (photo → idx → body → links, structurally parallel to `.book` — its own class, not a literal `.list-row` migration, same precedent as `.book` itself).
- Filtering is **two independent layers**, not one: `.filters-wrap` holds two `.filter-group`s ("Follow For" and "Trust Score"), each its own `.filter-select-wrap` > `<select class="filter-select">` tagged `data-filter-group="follow"` / `data-filter-group="tier"` (a `change` listener reads `select.value` and toggles a `.filter-select-wrap.is-active` class when it isn't `"all"`, mirroring the old chip's filled active state). A person is shown only if it matches the selected option in *both* groups (AND, not OR) — the script tracks `activeFilters.follow`/`activeFilters.tier` independently and re-applies both on every change, rather than the book shelf's single-filter-variable script. A person can carry **several** follow-for tags at once (`data-categories="apologetics textual-criticism debate-rhetoric"`, space-separated — "does *any* tag match" the selected option), but exactly **one** trust tier (`data-tier="tier-5"` — exact match). Don't copy the book shelf's filter script verbatim; the matching logic differs on both counts.
  - This was originally a wrapping row of `.chip` buttons (same shared atom as `worthy-books.html`), one button per category. It was switched to a native `<select>` once the Follow For category list grew past ~20 options and a chip row stopped being usable — a dropdown scales to a long option list far better than a row of pill buttons does. `.chip` itself is untouched and still lives on in `worthy-books.html`; this page just stopped using it. The select is styled (not a bare unstyled control) per the same "skin a native form element to match the site" precedent as the pill `<input type="email">` on `index.html` — `appearance: none` plus a custom chevron (a CSS `mask-image` reusing `.nav-drop-trigger`'s glyph, not a plain background-image, so its color can respond to hover/focus/active state) recreate the pill look, but the native `<option>` list still renders in OS chrome, not the site's own type styles — accepted tradeoff for free native keyboard/screen-reader/mobile support.
- **Trust score** is a shared 5-tier scale, worst → best: "Caribbean Death Apple" (consume this and you will die), "Rambutan Pit" (choking material), "Chicken Dinner" (consume with discernment), "Steak, Eggs and a Salad" (fill up regularly), "The Full Thanksgiving Meal" (you'll not find better) — all 5 tiers are named now, there's no more unnamed-tier state (the `.name.is-unnamed` style existed for that gap and has been deleted; don't reintroduce it unless a tier genuinely goes unnamed again). It is **not** displayed as a standalone block near the top of the page — it shows up in two places only: (1) as a hover/focus popover (`.badge-wrap` > `.trust-popover`, CSS-only via `:hover`/`:focus-within`, no JS) anchored to each person's `.person-badge`, and (2) as a full static copy (`.trust-legend`, reusing the same `.trust-legend-list`/`.trust-tier` markup) at the very bottom of `<main>`, right before the footer — this is the fallback for anyone who can't/won't hover (touch devices, keyboard users who don't tab to the badge). ### Art print shop (Stripe)

- Each of the 12 prints on `art.html` has a "Buy a Copy" button (`.btn-buy`) linking directly to a Stripe **Payment Link** (`https://buy.stripe.com/...`), opened in a new tab (`target="_blank" rel="noopener"`, same convention as the external buy links on `worthy-books.html`). Payment Links are Stripe-hosted checkout pages — there's no backend involved, which is why this approach was chosen for a static, no-build-step site instead of server-created Checkout Sessions.
- `stripe-setup/` is a standalone Node tooling directory (own `package.json`; `node_modules/` and `.env` are gitignored) used only to provision Stripe objects. It is **not** part of the deployed site and nothing on any page loads it.
  - `.env` (gitignored, never committed) holds `STRIPE_SECRET_KEY` / `STRIPE_PUBLISHABLE_KEY`; `.env.example` documents the expected shape with placeholder values only. The publishable key isn't actually used by anything yet — Payment Links need only the secret key server/script-side. It'd only matter if the site ever embeds client-side Stripe.js/Elements directly instead of redirecting to `buy.stripe.com`.
  - `npm run test-connection` — sanity-checks `STRIPE_SECRET_KEY` via `stripe.balance.retrieve()` and reports whether it's a TEST or LIVE key.
  - `npm run create-payment-links` — provisioning script: for each of the 12 prints, creates (or reuses, matched via a `cc_slug` metadata tag on the Stripe Product) a Product + Price ($12.95 flat, USD) + Payment Link (adjustable quantity 1–10, US-only shipping address collection), plus one shared Shipping Rate ($6.95 flat, reused across all 12). It's safe to re-run: it searches for existing objects by metadata before creating anything, so it won't create duplicates. Results are written to a gitignored `payment-links.json`. Whichever key is in `.env` at run time determines whether this creates test or live objects — test and live are fully separate object graphs in Stripe.
  - `npm run find-live-payment-links` — read-only lookup script (creates nothing) that searches live-mode Stripe for the 12 `cc_slug`-tagged Products/Payment Links. This exists because the live objects here were provisioned by using Stripe Dashboard's "copy to live mode" feature on the test-mode objects, not by re-running `create-payment-links.js` with a live key — this script's only job is finding the resulting live Payment Link URLs so they can be pasted into `art.html`.
  - `npm run update-product-images` — finds each of the 12 `cc_slug`-tagged Products (same metadata search as the scripts above) and, if its current `images[0]` doesn't already match `${SITE_ORIGIN}/hms-art/<slug>.jpg`, calls `stripe.products.update()` to fix it. Written for the `crownandcalling.org` → `hismajestyssons.com` domain/folder rename: Products created before that rename still point their image URL at the old domain+folder combo, and this is the one-time fix. Idempotent (skips products already correct) and non-destructive (only touches `images`, never creates/deletes). Must be run once per key — test key fixes test-mode Products, live key fixes live-mode Products, since they're separate object graphs. Results are written to a gitignored `update-product-images-results.json`.
  - `npm run update-product-descriptions` — same shape as `update-product-images` but for the `description` field: Products created before the Crown & Calling → His Majesty's Sons rename still have descriptions starting "Crown & Calling art print. …", frozen at creation time. Recomputes the expected description per slug (own copy of the `PIECES` scripture list, matching `create-payment-links.js`) and updates only products whose description doesn't already match. Idempotent, only touches `description`, must be run once per key (test/live), results written to a gitignored `update-product-descriptions-results.json`.
- Stripe Product images point at `https://hismajestyssons.com/hms-art/<slug>.jpg` (the live domain's full-size JPGs, not the `-sm` thumbnails used on the page itself) — Stripe requires a publicly reachable URL, so these only resolve once the matching `art.html`/`hms-art/` state is actually deployed.
- Test-mode Payment Link URLs contain a `test_` segment (e.g. `buy.stripe.com/test_...`); live ones don't — that's the only way to tell which mode a URL in `art.html` belongs to just by looking at it.

### Social engine (video generator for social posts)

- `social-engine/` is a standalone Node/[Remotion](https://www.remotion.dev) tool that generates on-brand social video clips (HMS logo + user-entered text, optional music and a CSS background pattern) sized for Instagram and X. Same shape as `stripe-setup/` above: its own `package.json`, gitignored `node_modules`, not part of the deployed site, no build-step impact on the site itself.
- **Full docs live in `social-engine/README.md`** — setup, running Remotion Studio (the interactive props-editing UI), rendering from the CLI, adding music, the background-pattern system, and known Chromium rendering gotchas (jpeg vs. png frame capture, blurry tiled SVG backgrounds). Read that file before making changes here rather than duplicating its detail in this one.
- At a glance: `src/Root.jsx` defines the `Square` (1080×1080) and `Vertical` (1080×1920) compositions; `src/SocialPost.jsx` is the actual clip content; `src/schema.js` is a Zod schema attached to each composition so Remotion Studio renders a real form (textarea/dropdown) instead of a raw JSON props editor; `src/backgrounds/` is a small hand-maintained registry of swappable CSS background patterns (`none`/`grid`/`diagonal`/`cross`); `src/tracks.js` is the equivalent registry for selectable music tracks, but auto-generated from whatever's in `public/music/` by `scripts/generate-tracks.js` rather than hand-edited. `audioStartSeconds` (plain number field, seconds into the source file) shifts which part of the track plays without changing the clip's length — figure out the value by ear in any player, no in-repo tooling for it. `scripts/generate-tracks.js` also probes each track's duration via `ffprobe` into `TRACK_DURATIONS` (`src/tracks.js`), which `schema.js` validates `audioStartSeconds` against — an offset that would run past a track's end is now a clear Zod error instead of a silent, sound-free render.

### The Armory (sin/scripture battle map + memorization game)

- `armory.html` is the Make War dropdown's single link (label "The Armory"), replacing an earlier bare "Coming Soon" placeholder page (`make-war.html`, deleted). It ships two toggleable views over one shared dataset and one shared progress state — a **Dossier** view (flat scannable card grid, fast lookup on a phone) and a **Map** view (radial "campaign map": a center command post with 9 sin-territory nodes arranged around it, closer to center = higher threat tier = more dangerous) — plus one search box that filters identically in both (Dossier hides non-matching `.card`s via the `hidden` attribute, same convention as `worthy-men.html`/`worthy-books.html`'s filter scripts; Map dims/highlights non-matching `.node`s instead, since hiding a node would break the radial geometry).
- Content lives in `armory-data.js` (no logic, no DOM): `window.ARMORY_TIERS` (4-tier threat scale — Skirmish/Siege/Stronghold/Total War, worst-to-best inverted from `worthy-men.html`'s trust scale since here *higher* tier means *more dangerous*, not more trustworthy), `window.ARMORY_DATA` (9 sins × 3 KJV verses each), `window.ARMORY_RANKS` (10-rank cosmetic leveling ladder, Squire → Champion of the King). Each verse has a permanent `id` (`${sinId}-${slug}`, e.g. `"lust-1cor10-13"`) used as its `localStorage` progress key — this must never be reassigned/reused once shipped, since a profile's saved mastery is keyed by it — plus a hand-authored `chunks` array (clause-sized phrases whose ordered concatenation reproduces `text` exactly) that feeds the tap word-order drill; KJV punctuation is too inconsistent for chunks to be derived automatically, so adding a verse later means authoring both `text` and `chunks` by hand.
- The threat-tier *names* are deliberately **not** spelled out anywhere in the visible UI — an earlier version showed a top-of-page legend row plus a pill "chip" naming the tier on every card/sheet (e.g. "STRONGHOLD"), both were removed as unhelpful noise. Only the tier *color* remains as a visual severity cue (card left border, `.badge-hex` border/ring, map node color/position); the tier name survives in exactly one place — each map node's `aria-label` — for screen-reader context that doesn't clutter the visual page. Don't reintroduce a visible tier-name chip/legend without a fresh reason; if you do, `design-system/index.html`'s "Threat-tier badge" specimen and this note both need updating.
- Progress/profiles live in `armory-state.js` (pure logic, no DOM), mirroring `theme.js`'s shape exactly: a `window.CC.armory` sub-namespace of getter/setter functions, backed by a single `localStorage['cc-armory']` key, with `cc-armory-profilechange`/`cc-armory-progresschange` `CustomEvent`s for cross-component reactivity instead of polling. Profiles are browser-only and unsynced (no accounts, no PIN — a family shares one device/browser and switches via a "Who's Fighting?" picker), each tracking its own per-verse mastery, XP, and settings independently. A sin's "conquered" state is always derived (every one of its verses at `status: "mastered"`), never stored, so it can't drift if content is edited later. On load, an unrecognized or corrupt `schemaVersion` is never silently discarded — the raw blob is preserved under a `cc-armory-<tag>-backup` key and a fresh store is started, so a future migration could still recover it.
- The mastery drill (`armory.js`) is device-adaptive: `pointer: coarse` (falling back to the site's existing `≤720px` mobile breakpoint) defaults to a **tap word-order game** (shuffled phrase chips tapped into place, no typing), anything else defaults to **full free-text recall** (typed from memory, checked with lenient matching) — always manually overridable per-profile via a mode switch link right inside the drill modal. The free-text matcher normalizes both texts (lowercase, punctuation stripped except word-internal apostrophes, whitespace collapsed) and compares them with **word-level Levenshtein edit distance** (each word is one comparison unit, so a wrong word and a missing word are weighted equally — not character-level distance), accepting within `max(2, ceil(wordCount * 0.15))` edits (~15% tolerance, floored at 2 so short verses aren't punished to zero slack); the same DP backtrace used to score the attempt also classifies each word match/substituted/missing for the highlighted feedback, no second pass. Mastery is **mode-agnostic and sticky**: either drill type can produce mastery (2 consecutive correct attempts, of either mode, not necessarily back-to-back), and once mastered a verse's status never reverts on a later miss — this is an encouragement tool, not a graded exam.
- XP/leveling is cosmetic only and never gates content — every verse and every sin is attemptable by anyone at any level. XP is awarded once per verse on first mastery and once per sin on first full conquest (both idempotent via the state transition itself, not a separate "already awarded" flag). Leveling unlocks a rank title, a thicker/glowing avatar-frame ring, and — on the Map view only — visibly grows the command post's cosmetic detail in `data-level-stage="1".."5"` increments (outer ring → banner flags → dashed ring → crown-points motif), all pure CSS gated by the attribute, no JS-driven DOM rebuild per level.
- Avatars are hand-built vector, not commissioned art (no image-generation tool available in this environment): 8 simple stroke-based line-icon `<symbol>`s — crown, sword, shield, anchor, ship's wheel, chalice, great helm, banner (knightly/naval/Christian, defined once in `armory.html` and referenced via `<use>`) — × 6 colors (the 4 threat-tier colors + `--accent` + one neutral) — matching the site's one real icon precedent (nav's chevron/sun-moon/hamburger icons), not the complex text-outline logo SVGs in `assets/`. Each sigil button carries a `title`/`aria-label` naming it (e.g. "Ship's Wheel") since the abstracted line art alone isn't always self-explanatory at 22px.
- The conquest celebration (badge seal-and-ring animation, spark burst, map supply-line solidifying, a banner pill) is scoped entirely to `armory.html`'s own `<style>` block with `armory-`-prefixed `@keyframes` names — it's the **first and only `@keyframes` usage anywhere in this codebase** (confirmed via repo-wide grep before building it), so don't assume a shared motion-utility file exists; if a second feature ever wants this vocabulary, promote it to `site.css` then, per the same "promote only when duplicated across ≥2 pages" rule as everything else. All of it respects `prefers-reduced-motion: reduce` by skipping the motion and applying end-states instantly — no information is motion-gated.
- Armory declares its own page-scoped design tokens in `armory.html`'s `<style>` block (`--t1`…`--t4` for the threat tiers, `--armory-panel`/`--armory-panel-2` for card/surface backgrounds, `--hairline-strong`, `--hud` for the condensed uppercase tag/label typeface) using deliberately new names — it never redefines `site.css`'s real `--paper-2`/`--rule`/etc at `:root`, which would silently reskin those tokens for every other component on the page (nav, footer, buttons) that also reads them. `[data-scheme="ink"]` overrides these the same way `site.css` itself does (not a `prefers-color-scheme` media query or a fake demo toggle — early prototypes for this feature used both and neither is right for a page that must obey the site's real `theme.js`/`.theme-toggle`).

## Working conventions

- Don't try to verify visual/CSS changes yourself (installing Playwright, chromium-cli, screenshotting, etc.). The user verifies visual changes in their own browser. Make the change, explain what you changed and why you expect it to render correctly, and stop there.

- Adding a new sub-page: copy the structure of an existing static page (`<link rel="stylesheet" href="site.css">`, `<script src="theme.js"></script>` in `<head>`, the `.nav-toggle` button, `id="nav-links"`, and all four `.nav-drop` blocks (Lead/Learn/Make War/Build) in the nav markup, the full `.foot-brand`/`.foot-links`/`.foot-social` footer, the scroll-listener + hamburger-menu + multi-dropdown script before `</body>`) rather than the React pattern used by `index.html`.
- `.mark .sigil img { width: 100%; height: auto; }` in `site.css` only applies inside `.mark` — a bare `.sigil` (as used standalone on the design-system page) needs its own sizing rule or the logo SVG renders at native/huge size.
